## 1. 总体结论

Phase 8 的主实现方向是对的：

- Okapi BM25 公式、IDF 变体、文档长度归一化和 `k1=1.2` / `b=0.75` 默认参数符合
  常见定义；分数降序、来源类型与编号升序的 tie-break 是确定性的；
- ASCII 标识符 / 版本号 / 优先级整串保留，中文 unigram + bigram，NFKC 与
  casefold 的作用有测试覆盖；
- 实验固定 Phase 6 的 `entity+heading` Chunk 粒度，离线重建语料，不调用
  Embedding；没有把 BM25 分数与 cosine distance 混为一谈；
- 报告明确说明了小样本、中文分词局限、`ILIKE` 延迟不含 SQL 扫描、负样本误召回
  很高，以及 Phase 9 才做融合，符合 Evidence First 和阶段边界；
- Phase 7 上次 review 中的延迟一致性、批次 / timeout / 服务端模型元数据、
  Gold Set 同源偏差、旧实验表清理、Settings 复制、文档命名和报告一致性测试，
  大部分已经实质闭环。

但本次增量仍有 **1 个高优先级问题**：实验脚本的 `--top-k` 是可变参数，而指标
始终固定为 Recall@5 / Recall@10；只要用非 10 的 `--top-k` 生成结果，manifest
中的 `recall@5` / `recall@10` 就不再是它们名字所表示的含义。默认命令得到的结果
恰好一致，所以现有报告数字没有错，但实验接口会静默生产错误口径的结果，不能视为
只是文档小瑕疵。

另有若干中优先级问题集中在可追溯性和证据完整性：

- 提交进仓库的 Phase 8 manifest 记录的 `git_commit` 是 `2ffd7a7`，
  比 Phase 8 功能提交 `567a714` 早，且 `git_dirty=true`，不能证明结果来自
  当前提交；
- 报告的一致性测试没有真正解析 `exact_priority` 分类行；
- “复用同一批 6 条 Defect”的表述与实际新增 `BUG-1234` 不符；
- BM25 的 `matched_terms` 在中文长串中可能只是一串单字，不足以支撑报告所强调的
  “可解释”；
- `KnowledgeChunkService.lexical_search()` 每次查询全量加载 Chunk 并重建索引，
  文档已标注为小规模实验实现，但尚无查询端到端耗时或规模边界测试。

总体上，**Phase 8 可以作为 BM25 基线进入下一步，但不建议在修正 top-k 指标口径
和 manifest 可追溯性之前，把这份 manifest 当作可长期引用的实验事实源。**

## 3. 高优先级发现

### 3.1 `--top-k` 可变，但指标固定为 Recall@5 / Recall@10

- 位置：`scripts/lexical_experiment.py:94-127`、`app/evaluation/lexical_experiment.py:123-136`
- 脚本允许 `--top-k` 取任意正整数，并把它传给 `evaluate_searcher(...)`；
- `_evaluate_queries` 却始终构造 `RetrievalEvaluation(k_values=(5, 10))`，
  只把 `searcher.search(query, limit=top_k)` 的结果交给评测器；
- 因此当 `top_k < 10` 时：
  - 结果列表长度不足 10，`recall@10` 实际只是“最多 top-k 的命中率”；
  - 若 `top_k < 5`，`recall@5` 也一样被悄悄截断；
- 本次实测 `--top-k 1` 得到 BM25 的 `recall@5 = recall@10 = 0.500`，
  明显不是 Recall@5 / Recall@10，但 manifest 仍使用这两个字段名。

**影响**

默认 `--top-k 10` 时，现有 Phase 8 报告和 manifest 的指标是自洽的，复跑也一致；
问题是这个实验入口不能被安全地用于 top-k 扫描。后续如果要用脚本比较 Top-5、
Top-20 或不同候选深度，会得到看似合法但含义错误的指标，进而误导 Phase 9 的融合
参数选择。

**建议**

1. 二选一：要么把 `--top-k` 限制为 `>= 10` 并明确它只是检索候选深度；
2. 要么让 `_evaluate_queries` 根据有效 K 值动态输出指标，例如只输出
   `recall@{k}`，并在 manifest 中记录 `top_k` 与 `k_values`；
3. 增加 `--top-k 1` / `--top-k 5` 的测试，断言不会生成名为 Recall@10 的
   错误指标。

## 4. 中优先级发现

### 4.1 提交的 Phase 8 manifest 指向 Phase 8 之前的提交且为 dirty

- 位置：`results/lexical-phase8.json:4-15`
- 已提交 manifest 中：
  - `git_commit = 2ffd78784df92d8c53abe6f1d0d65d2c489ad2`（即 `2ffd7a7`）
  - `git_dirty = true`
- 但当前 HEAD 是 `567a714`，Phase 8 的代码、数据集、报告和 manifest 都在
  `567a714` 中；`2ffd7a7` 是 Phase 7 修复提交。
- 本次重新运行得到 `git_commit = 567a714...`，指标相同，说明“数值可复现”；
  但这不能证明仓库中提交的这份 JSON 是在 `567a714` 上无改动生成的。

**影响**

证明链变成了：

```text
提交的 manifest 声称来自 2ffd7a7（且工作区脏）
        !=
Phase 8 功能实际所在的 567a714
```

后续接手者只读 manifest 时，无法从 `git_commit` 找回生成它的代码版本；如果未来
`2ffd7a7` 和 `567a714` 的 BM25 行为发生差异，这份 JSON 的审计价值会进一步下降。
这与上次 review 强调的“报告 / manifest 必须可追溯到同一事实源”是同一类问题。

**建议**

在干净的 `phase-8-bm25` 提交上重跑实验并提交新的 manifest；或者把
`git_commit` 改为明确的 `result_commit` / `report_baseline_commit`，
并额外记录 `HEAD` 与 `git_dirty` 的生成上下文。至少不要让已提交 manifest 的
`git_commit` 永久指向功能提交之前的状态。

### 4.2 Phase 8 报告一致性测试漏检 `exact_priority` 分类

- 位置：`tests/test_lexical_experiment.py:152-169`、
  `docs/LEXICAL_SEARCH_EXPERIMENT.md:104-112`
- 测试用正则解析分类表：
  ```python
  r"^\| `(?P<name>[^`]+)` \| (?P<ilike>[0-9.]+) \| "
  r"\*\*(?P<bm25>[0-9.]+)\*\* \| (?:\*\*)?(?P<mrr>[0-9.]+)(?:\*\*)? \|$"
  ```
- `exact_priority` 的 BM25 Recall@5 是 `0.833`，报告中没有加粗，
  因此该行不匹配这个正则；
- 实际解析只得到 `exact_identifier`、`exact_version`、`semantic_paraphrase`
  三行，`exact_priority` 完全没被断言。

**影响**

当前报告数字与 manifest 实际一致，这属于测试覆盖漏洞而非已发生的数据错误。但一旦
`exact_priority` 的数字发生漂移，测试仍会通过；这与“防止报告数字漂移”的测试目的
相冲突。尤其 `exact_priority` 恰好是 BM25 唯一 Recall@5 低于 1.0 的可回答分类，
是需要重点守护的行。

**建议**

- 解析时同时接受加粗和非加粗数字；
- 先断言分类集合等于 manifest 中除 `unanswerable` 外的全部分类集合；
- 用参数化或独立断言逐类比较，而不是只遍历“成功匹配到的行”。

### 4.3 “复用同一批 6 条 Defect”与数据集实际不一致

- 位置：`docs/LEXICAL_SEARCH_EXPERIMENT.md:27-33`、`eval/fixtures/phase8_simulated.json:162-175`
- 报告称 Phase 8 “复用同一批 12 条 TestCase、6 条 Defect、5 条 Requirement 和
  3 篇 Markdown 文档”；
- 与 Phase 6 数据逐实体比较后，Phase 8 的 TestCase / Requirement / Document
  确实是同一批；Phase 8 的 Defect 是 Phase 6 的 6 条加新增 `BUG-1234`，
  共 7 条；
- 新增 `BUG-1234` 正是报告 §4.3 的组合关键词坏例和 §2 的示例来源，所以它不是
  无关数据，而是实验设计的一部分。

**影响**

当前 47 个 Chunk 的数量和指标都是正确的，但“复用 6 条 Defect”的表述会让读者
误以为 Phase 8 与 Phase 6 的语料完全相同。该差异会改变 BM25 的文档频率和 IDF，
因此不能被当作纯文字错误忽略；应在报告中明确“新增 1 条 Defect 用于组合标识符
案例”，并说明这正是 Phase 8 不再完全复用 Phase 6 语料的原因。

**建议**

修正报告为“复用 12 条 TestCase、5 条 Requirement、3 篇文档，并新增 1 条
Defect（`BUG-1234`）”；如果希望在语料层面完全隔离变量，则应把该 Defect 放入
单独的 Phase 8 数据集，并在报告里明确不再声称复用 6 条 Defect。

### 4.4 BM25 的 `matched_terms` 对中文长串的可解释性有限

- 位置：`app/retrieval/lexical.py:51-74, 162-207`、
  `scripts/lexical_experiment.py:130-140`
- 当前分词为中文字符 unigram + bigram；`search` 的 `matched_terms` 记录的是
  实际命中的 query token；
- 对一条中文 Query，命中项可能只是单字和跨词 bigram，例如“支、付、超、时、
  支付、付超、超时”；这能解释“为什么有词项交集”，但不能直接解释“为什么这条
  证据回答了问题”；
- 测试 `test_combined_query_uses_all_terms_and_is_explainable` 只验证了含四个
  ASCII 标识符的组合 Query，没有覆盖中文 Query 的解释输出。

**影响**

报告把 BM25 定位为 Phase 9 的“可解释排序分数”。ASCII 编号场景这一点成立，
但中文 Query 的 matched_terms 需要读者二次推断分词结果。若未来把 matched_terms
直接暴露给用户，可能产生比现有 `matched_on` 更嘈杂的解释。

**建议**

- 在文档中明确 matched_terms 是“分词后的词项”，不是“命中的业务概念”；
- 为中文 Query 增加一个测试，固定其输出形态；
- Phase 9 暴露给 API 时，考虑只展示原 Query 中的连续片段或可读词，而不是所有
  unigram / bigram。

### 4.5 PostgreSQL 路径未在本轮复验，且服务层是全量加载 + 查询时建索引

- 位置：`app/services/knowledge_chunk_service.py:190-234`、
  `tests/test_retrieval_pg.py:17-49`
- `lexical_search()` 每次查询执行 `select(KnowledgeChunk)`，没有数据库侧关键词
  预过滤，然后把全部候选 Chunk 转成 Python 对象并构建 `BM25Index`；
- 文档已明确“适用于当前小规模知识库”“大库应改为持久化倒排表 / 搜索服务”，
  这一点做得好，没有把实验实现包装成生产方案；
- 但当前只有 47 个 Phase 8 Chunk 的离线测试，以及一条 PostgreSQL 集成测试；
  没有记录查询端到端 P50 / P95，也没有测试 1k / 10k Chunk 下的内存和延迟退化；
- 本次未运行 PostgreSQL 全量测试，因此不能把 `test_retrieval_pg.py` 的新增路径
  标记为本轮实机通过。

**影响**

Phase 8 的报告延迟只测了应用层内存索引，不包含 SQL 全表拉取、ORM 对象构建和
BM25 重建；这些操作在大库上会成为主要成本。当前结论用于小样本基线可以接受，
但不能据此支持生产容量判断。

**建议**

- 在报告已知局限中增加“服务层每次查询都全量读取并建索引，未测端到端耗时”；
- 增加一个至少 1k Chunk 的合成规模测试，记录耗时上界或 `xfail` / 标志性告警；
- Phase 9 若要复用该接口，先决定候选预过滤策略，避免融合时每个 Query 都
  对全表建两次索引。

  `app/evaluation/lexical_experiment.py:58-79` 已明确说明这一点，报告 §7 也写了

  对比。
- **L8 新增 `tests/services/test_knowledge_chunk_service.py` 覆盖了 source_types
  与 limit，但没有覆盖未知 source_type / 空 Query / 全停用词 / 非法 limit 的
  服务层组合。** 纯函数层有部分覆盖，服务层仍主要依赖调用方保证输入。
